# AvaNevis v3.1.0 Design and Implementation Plan

**Branch:** `release/3.1`  
**Date:** 2026-11-21  
**UX Design Companion:** [v3.1.0 UX & Visual Design](2026-11-21-v3.1-ux-designs.md)  
**Goal:** Ship AvaNevis **v3.1.0** by fixing the root causes of the v3.0 Chat `"Not enough matching information..."` failure and upgrading local Q&A intelligence, adding 11 canonical recording tags (`Meeting`, `Appointment`, `Phone / Support Call`, `Interview`, `Lecture / Study`, `Podcast`, `Video`, `Voice Note`, `Brainstorm`, `Music`, `Other`) with dedicated per-tag summary templates replacing the current meeting-notes-only pipeline, adding non-destructive post-recording and optional pre-summarization speaker name assignment, opening the local Summary & Chat catalog to **Gemma 4** and **Inkling 2 Mini** alongside **Qwen3.5**, and sweeping dependencies to the latest compatible releases.

**Approach:** Deliver in five sequenced phases so the Chat reliability overhaul lands first, metadata/tag/speaker foundations build cleanly on `meetings.json` + SQLite FTS5 schema v2 without invalidating `sourceTranscriptHash` captions, shared `llama.cpp` runtime decoupling unlocks multi-model switching (Gemma 4 & Inkling 2 Mini), and dependency/qualification gates close before release cut. Keep every feature 100% offline/local, plain HTML/CSS/JS on the renderer (`src/renderer/*-helpers.js`), isolated in `src/main/` services, and run via per-invocation Python 3.11 subprocesses.

**Constraints (canonical contracts — read before editing each surface):**
- **Privacy & Local AI:** No cloud inference, telemetry, analytics, or hidden background downloads. User HF tokens stay strictly in async `safeStorage` and validated stdin boundaries. All GPU jobs serialize on `aiComputeActionQueue`. See [local-ai.md](../../development/contracts/local-ai.md).
- **Recording & Persistence:** Separate `{stem}.capture/` spools mixed on stop; atomic `FileLock` + temp-file + `os.replace()` metadata writes; saved `.md` remains the immutable transcript source of truth; derived search/chat artifacts live under Electron `userData`, never the repo. See [recording.md](../../development/contracts/recording.md) and [meeting-persistence.md](../../development/contracts/meeting-persistence.md).
- **Packaging & Platforms:** Preserve Windows 10/11 x64, macOS 15+ Apple Silicon (`arm64`), and Linux x86_64 (Omarchy/CachyOS Hyprland/Wayland/PipeWire supported vs experimental tiers), Linux opaque device IDs, managed CUDA 12 fail-closed rules + Repair/Uninstall escape paths, Speakrs-only Linux diarization, and `AVANEVIS_PACKAGED=1` path hardening. See [packaging.md](../../development/contracts/packaging.md).
- **IPC & Facades:** Update owning `src/main/` service, `src/preload.js`, every renderer caller, and snapshot/characterization tests together; keep `src/main.js` a composition root and preserve `src/main-process-helpers.js` / `src/ai-addon-setup.js` export key sets. See [ipc.md](../../development/contracts/ipc.md).

## Section 0: Root-Cause Analysis — v3.0 Chat `"Not enough matching information..."` Failure

Direct inspection of `backend/history_qa/`, `backend/search/history_index.py`, and `src/main/history-qa-service.js` confirms why simple questions like `"what key points came up in the recording from 05/09/2026"` — and especially `"All recordings"` queries on Linux — fail with `Not enough matching information in the selected transcripts or summaries to answer that.` even when the footer reads `Searched 2 recordings · 6 matching excerpts`:

1. **Primary culprit — Over-strict per-sentence/per-line citation verifier silently discards valid LLM answers (`backend/history_qa/citation_verifier.py:165-204`):**
   - `verify_grounded_response()` splits every non-empty Markdown line into sentences and rejects the **entire response** (`unsupported = True`) if **any single line or sentence** containing `\w` lacks an inline `[Ek]` token.
   - Any natural LLM response containing a Markdown heading (`## Key Points`), a lead-in line (`Here are the key points from the recording:`), a GFM table header/separator (`| Topic | Detail |`), or a two-sentence bullet where `[E1]` is on sentence 2 triggers `unsupported = True`.
   - Worse, lines `200-204` return `{"ok": True, "needsRepair": False, "status": "insufficient_evidence", "answerMarkdown": INSUFFICIENT_EVIDENCE_MESSAGE}` — **zero repair retry** and **indistinguishable in UI** from a real lack of evidence, even though `qa_runner.py` never tells the model to avoid headings/intros and the v3.0 chat design explicitly encourages Markdown headings and GFM tables. This directly explains the user screenshot (`Searched 2 recordings · 6 matching excerpts` → yellow `insufficient_evidence` banner).

2. **Secondary culprit — Pure keyword FTS5 retrieval breaks on overview, date, and `"All recordings"` queries (`backend/history_qa/retrieval.py:123-132`, `backend/search/history_index.py:1241-1325`):**
   - `build_retrieval_query()` only strips basic English stopwords (`_QUESTION_STOPWORDS`), leaving query meta-words (`key`, `points`, `came`, `up`, `recording`, `summarize`, `decisions`, `follow`, `ups`, `recent`) as literal FTS5 search terms. That breaks even AvaNevis's own starter prompts (`src/renderer/chat-helpers.js:144-154`, e.g., `"What key points or decisions came up in my recent recordings?"`).
   - Dates such as `05/09/2026` are split on `/` into tokens `05`, `09`, `2026`. `m.date_iso` is **not indexed in `passages_fts`** (`history_index.py:661-668`), and `retrieve_evidence()` never parses date phrases into `dateFrom`/`dateTo`.
   - `match_and` returns 0 rows → `_query_passages` (`history_index.py:1321-1324`) falls back to `OR`, matching `"2026"` or `"Recording"` (present in default titles like `Recording 2026-09-05 08:44`) and casual speech tokens like `"up"` or `"came"` across **every recording in History**. On Linux (or any large history in `"All recordings"` scope), the global `MAX_EVIDENCE_BLOCKS = 12` / `MAX_PASSAGES_PER_MEETING_CANDIDATE = 6` budget fills up with random `"up"`/`"came"`/title matches from unrelated recordings instead of the target recording!

3. **Small-scope & overview context starvation (`backend/history_qa/retrieval.py:19-23, 272-279`):**
   - When the user scopes to 1 or 2 recordings (whose entire transcript + summary easily fits inside the 32,768-token context window), `retrieval.py` still forces keyword-only matching capped at `MAX_PASSAGES_PER_MEETING_CANDIDATE = 6` (~350-char blocks) and explicitly ranks `summary` passages **behind** `transcript` passages (`kind_tier` / `retrieval.py:274`). Asking for `"key points"` returns 6 narrow, disconnected ~15-second snippets instead of the recording's summary or full chronological flow.

4. **Defensive prompt, missing JSON mode & broken follow-up continuity (`backend/history_qa/qa_runner.py:124-202`, `src/main/history-qa-service.js:1100-1110`):**
   - The 8-line system prompt in `qa_runner.py:124-135` demands strict JSON without enabling `llama-server`'s `response_format: {"type": "json_object"}` (`call_llama_server` line 194), does not explain how to cite headings/lists/multi-sentence bullets, gives no guidance on partial answers or synthesis across passages, and encourages timid `insufficientEvidence: true` refusals.
   - Multi-turn follow-ups (`"what else did he say about that?"`) fail because `retrieval.py` ignores conversation history when selecting terms/meetings, and `history-qa-service.js:1105-1109` silently strips earlier turns if the new turn happens to cite different meeting IDs.

5. **Older transcripts missing `.captions.json` vs. legacy summaries (`backend/search/history_index.py:526-528, 574-604`):**
   - **Clarification on timestamps:** Missing `.captions.json` on older v1/v2 transcripts is **not** the primary cause of the failure — when captions are absent, `_build_passages_for_snapshot()` falls back to `_build_markdown_passages()` (`[MM:SS - MM:SS]` blocks) or `_chunk_plain_paragraphs()` (`history_index.py:808-812`).
   - **Actual legacy edge cases found:** (a) `_resolve_meeting_summary_text()` (`history_index.py:585-587`) silently skips legacy completed summaries that lack `sourceTranscriptHash` (from pre-hash v2.x releases), hiding the richest overview evidence from Search and Chat; (b) untimed plain-text fallback (`_chunk_plain_paragraphs`, line 415) always sets `speaker = ""`, discarding speaker context on untimed transcripts; and (c) `m.date_iso` is omitted from FTS5.

## Phase 1: Chat Reliability Overhaul & Intelligence Upgrade

### Task 1.1: Fix `citation_verifier.py` & Upgrade `qa_runner.py` Prompting, JSON Grammar & Streaming

**Files:**
- `backend/history_qa/citation_verifier.py` — fix Markdown-aware citation verification, add non-`<think>` reasoning tag stripping (Gemma `<|channel>thought...<channel|>`), and introduce `citation_repair` feedback path.
- `backend/history_qa/qa_runner.py` — upgrade system prompt, enable `response_format: {"type": "json_object"}` on `llama-server`, enrich evidence headers (`Tag`, `Summary` vs `Transcript` kind, human speaker name), and support SSE token streaming.
- `src/main/history-qa-service.js` — forward distinct failure reasons (`no_matching_excerpts` vs `insufficient_evidence` vs `verification_failed`), stream partial progress deltas over `history-qa-progress`, and preserve usable conversation history across turns.
- `src/main/chat-thread-store.js` — preserve extended assistant `status` / `failureReason` metadata safely.
- `src/renderer/chat-helpers.js` & `src/renderer/app.js` — render streaming drafts, distinct callouts + one-click Retry / Broaden Scope actions, and context scope feedback.
- `tests/python/test_history_qa.py`, `tests/js/history-qa-service.test.js`, `tests/js/chat-helpers.test.js` — add regressions for Markdown headings, GFM tables, multi-sentence bullets, citation repair, streaming chunks, and failure states.

**Implementation:**
1. **Block-level Markdown citation verification (`citation_verifier.py`):**
   - Parse `answerMarkdown` into logical Markdown blocks (headings, paragraphs, list items, blockquotes, table rows, fenced code blocks).
   - Exempt purely structural scaffolding from needing `[Ek]`: ATX headings (`# ...`), GFM table header & separator rows (`| Col |` / `|---|`), horizontal rules, and short colon-terminated lead-in lines (`"Here are the key points:"`) when immediately followed by a cited list or table.
   - Require every **factual** paragraph, list item, blockquote, and table data row to contain at least one verified `[Ek]` (removing the brittle per-sentence failure when `[E1]` closes a 2-sentence bullet or paragraph). Keep hallucinated-ID stripping (`[E99]` → `""`) and fail-closed zero-citation rejection (`inline_valid_ids` empty → reject).
   - If `parsed` is valid JSON with factual content and `insufficientEvidence: false`, but fails verification because inline citations were omitted/misplaced, return `needsRepair: True, reason: "missing_citations"` so `qa_runner.py` uses its 1-retry budget with a targeted citation-placement repair prompt instead of silently discarding the answer!
2. **Thinking/reasoning stripping & JSON grammar (`citation_verifier.py`, `qa_runner.py`):**
   - Extend `strip_model_artifacts()` to strip both `<think>...</think>` (Qwen/DeepSeek) and `<|channel>thought...<channel|>` (Gemma 4) blocks.
   - Pass `"response_format": {"type": "json_object"}` in `call_llama_server()` (supported natively by `llama-server` OpenAI-compatible API).
3. **System prompt & evidence formatting upgrade (`qa_runner.py`):**
   - Replace the defensive 8-line prompt with explicit guidance: synthesize across multiple `[Ek]` passages (and summaries), answer partially when some parts of a multi-part question are in evidence (and clearly note what wasn't covered), format cleanly with concise Markdown headings/bullets/tables placing `[E1]` at the end of each bullet/claim/table row, and only set `insufficientEvidence: true` when none of the passages address the question.
   - Format evidence headers with kind + tag + date + timestamp + speaker: `[E1] Recording: <Title> [<Tag>] (<YYYY-MM-DD>, Summary | MM:SS, Speaker: <Name>)`.
4. **Honest error states & streaming (`qa_runner.py`, `history-qa-service.js`, `app.js`):**
   - Separate `no_matching_excerpts` (0 retrieval hits), `insufficient_evidence` (model explicitly judged evidence insufficient), and `verification_failed` (model failed formatting/citation verification after repair) so users see honest diagnostics instead of one opaque message.
   - Stream `llama-server` SSE chunks in `qa_runner.py` → emit bounded `progress` events (without exposing raw JSON keys — display clean status or progressive answer preview once `answerMarkdown` begins) and keep `llama-cli` non-streaming fallback intact.

**Validation:**
- `npm run test:python -- -k "history_qa"` — test answers with `# Headings`, intro lines, GFM tables, multi-sentence bullets, partial answers, Gemma thought tags, and missing-citation 1-pass repair.
- `node --test tests/js/history-qa-service.test.js tests/js/chat-helpers.test.js`.

### Task 1.2: Smart Local Retrieval (Date/Entity/Tag Parsing, Intent Routing, Small-Scope Coverage & Follow-Up Continuity)

**Files:**
- `backend/search/history_index.py` — bump `INDEX_SCHEMA_VERSION = "2"`, index `tag` and `speaker_names_hash`, allow indexing completed legacy summaries lacking `sourceTranscriptHash` (when transcript wasn't superseded), extract inline speaker names during untimed fallback, and expose lightweight meeting metadata lookup (`list_indexed_meeting_headers`).
- `backend/history_qa/retrieval.py` — add date/temporal parsing, entity pre-matching, query intent routing (`overview` vs `targeted` vs `follow_up`), meta-word stopword expansion, small-scope full/chronological coverage, neighbor `seq_index` (`k±1`) context expansion, and cross-recording diversity cap.
- `src/main/history-qa-service.js` — pass recent thread turn context (`lastCitedMeetingIds`, recent user/assistant questions) to retrieval preflight and retain thread history turns when thread scope stays consistent.
- `tests/python/test_history_qa.py` & `tests/python/test_history_index.py`.

**Implementation:**
1. **FTS5 Index Schema v2 (`history_index.py`):**
   - Bump `INDEX_SCHEMA_VERSION` from `"1"` to `"2"` (automatically triggers safe atomic rebuild via `_schema_is_valid()`).
   - Add `tag TEXT NOT NULL DEFAULT ''` and `speaker_names_hash TEXT NOT NULL DEFAULT ''` to `indexed_meetings` and update `title_hash` / change-detection tuple so tag changes or speaker-label renames incrementally re-index only that meeting.
   - Index legacy completed summaries when `ai.summary.status == 'completed'` and `summary_meta.get('sourceTranscriptHash')` is missing/empty (while still rejecting an explicit mismatched hash), restoring summary evidence for pre-v2.10 recordings.
2. **Deterministic Date & Temporal Resolution (`retrieval.py`):**
   - Parse explicit dates (`YYYY-MM-DD`, `DD/MM/YYYY`, `MM/DD/YYYY`, `"5 Sep 2026"`, `"Sep 5, 2026"`) and relative phrases (`today`, `yesterday`, `this week`, `last week`, `most recent`, `latest recording`) into concrete `dateFrom`/`dateTo` constraints (disambiguating `05/09/2026` against actual `date_iso` prefixes present in `indexed_meetings` — if `2026-09-05` exists and `2026-05-09` does not, pick `2026-09-05`!).
   - Strip matched date tokens from keyword search so `"05/09/2026"` acts as a date filter instead of an `OR "2026"` wildcard across all recordings!
3. **Query Intent Classification & Entity Matching (`retrieval.py`):**
   - Pre-match recording titles, speaker names, and canonical tags in the scoped `indexed_meetings` / `passages` table (e.g. `"Amir Andy Sync"`, `"Andy"`, `"Interview"`).
   - Expand `_QUESTION_STOPWORDS` with retrieval meta-words (`key`, `point`, `points`, `main`, `recording`, `recordings`, `meeting`, `meetings`, `summary`, `summarize`, `summarized`, `overview`, `notes`, `highlight`, `highlights`, `decision`, `decisions`, `action`, `item`, `items`, `task`, `tasks`, `follow`, `followup`, `recent`, `latest`, `last`, `today`, `yesterday`, `week`, `month`, `file`, `transcript`, `transcripts`).
   - Route to **`overview` mode** when: (a) scoped or date/entity-matched meetings are few (`<= 3` recordings) AND the cleaned keyword query is empty or asks for key points / summary / decisions / topics / timeline; OR (b) scoped to `selected_meetings` (`1–3` meetings) whose total text fits comfortably in budget.
     - In `overview` mode: prioritize `summary` passages first, then chronologically ordered `transcript` passages (`seq_index ASC`) covering up to `20,000` evidence tokens / `40` blocks (well inside `32,768` ctx with 4K history + 2K system/output reserve). If a single meeting is larger than the token budget, uniformly sample across start/middle/end so the full arc is represented!
   - Route to **`targeted` mode** otherwise:
     - Require non-boilerplate body matches first (`matchedBody=True`), explicitly demoting title-only matches on generic words (`Recording`, year digits) so `"All recordings"` searches on Linux never fill up with `"Recording 2026-..."` title hits.
     - Enforce per-meeting diversity cap (e.g. max 3 passages/meeting initially when `matchedMeetingCount > 4`) so one noisy recording cannot crowd out other recordings.
     - Expand top transcript hits with ±1 adjacent `seq_index` neighbor passages from the same meeting before merging, preventing mid-thought truncation.
4. **Follow-up Thread Continuity (`history-qa-service.js`, `retrieval.py`):**
   - Pass prior cited `meetingIds` and last question tokens from the active thread into `retrieval.py` when `historyTurns` exist. When a follow-up has sparse/pronoun-only content (`"what did she decide?"`, `"tell me more"`), anchor retrieval to the previous turn's cited meetings rather than returning 0 hits.
   - Update `history-qa-service.js:1105-1109` so recent conversation turns within the same thread scope are retained (bounded by `MAX_HISTORY_TOKENS`) rather than dropped whenever cited IDs shift.
5. **Preserve Local-AI Invariants:** Zero-hit preflight still runs **before** `aiComputeActionQueue` acquisition (`history-qa-service.js:1055-1084`) so genuinely unindexed/empty scopes allocate zero VRAM and never start `llama-server`.

**Validation:**
- `npm run test:python -- -k "history_qa or history_index"` — add dedicated tests for: `05/09/2026` date parsing + disambiguation, `"what key points came up in the recording from 05/09/2026"`, `"All recordings"` query with `"2026"`/`"Recording"` boilerplate titles, overview mode fitting 1–2 full transcripts + summaries, legacy summaries without `sourceTranscriptHash`, and pronoun follow-ups.

## Phase 3: Speaker Label Assignment (`Speaker N` → Human Names)

### Task 3.1: Non-Destructive `ai.diarization.speakerNames` Overlay & Backend Propagation

**Design Decision (Preserving `sourceTranscriptHash`):**
Editing committed `.md` files directly on disk to replace `**Speaker 1:**` with `**Alice:**` would immediately break `sourceTranscriptHash` across `.captions.json` (disabling SRT/VTT subtitle export), `.speakers.json` (causing `summary_runner.py` to fall back to `.md`), `ai.summary.sourceTranscriptHash` (dropping existing summaries from FTS5 search), and `summary-language-helpers.js` (losing confirmed summary language), while breaking `SPEAKER_PREFIX_RE` in `history-detail-helpers.js:11` and `summary_pipeline.py:24`. Instead, store a **non-destructive overlay map** `ai.diarization.speakerNames` inside `meetings.json`:

**Files:**
- `backend/meetings/paths.py` — allow `speakerNames` inside `normalize_ai_feature_metadata(manager, 'diarization', ...)` as a `dict` mapping canonical keys (`Speaker 1`..`Speaker 99` or `SPEAKER_XX`) to sanitized display names (UTF-8 trimmed, single-line, max 64 chars, stripped of `*`, `\n`, `\r`, and `-->` so Markdown/SRT/VTT output cannot be injected; empty/whitespace string deletes the override).
- `backend/meeting_manager.py` — accept `speaker_names` via `update_meeting` / `update_meeting_ai` (and propagate to `get_meeting` / `list_meetings`). Existing `commit_transcription_attempt()` already pops `ai.diarization`, ensuring re-transcription cleanly resets speaker overrides.
- `backend/search/history_index.py` — read `ai.diarization.speakerNames`, remap `speaker` on both `.captions.json` cues and `.md` passages before FTS5 insertion, and include `sha256(json.dumps(speakerNames, sort_keys=True))` in `speaker_names_hash` so renaming `Speaker 1 → Alice` immediately re-indexes that recording for both History Search and Chat Q&A!
- `backend/summaries/summary_runner.py` & `backend/summaries/summary_pipeline.py` — load `speakerNames` (passed from `summary-service.js` via `--speaker-names-json` or read securely from meeting metadata), apply mapped names to `load_summary_segments()` before prompt chunking, and store `speakerNamesHash` inside `ai.summary` metadata (optional field in `paths.py`) so the UI can detect post-summary speaker renames cleanly without invalidating `.captions.json` or FTS5. Also generalize `SPEAKER_PREFIX_RE` in `summary_pipeline.py:24` defensively to tolerate custom bold speaker headers (`^\*\*(?P<speaker>[^*\n:]{1,64}):\*\*\s*(?P<text>.*)$`) alongside `Speaker N`/`Unknown`.
- `src/main/meeting-manager-client.js`, `src/main/file-export-ipc.js`, `src/main/summary-service.js`, `src/renderer/subtitle-export-helpers.js` — apply `ai.diarization.speakerNames` when exporting `.md`, `.txt`, `.srt`, and `.vtt` (including WebVTT `<v Alice>` voice tags) and pass mapped names to summary generation.
- Tests: `tests/python/test_meeting_manager.py`, `tests/python/test_history_index.py`, `tests/python/test_summary_pipeline.py`, `tests/js/file-export-ipc.test.js`, `tests/js/subtitle-export-helpers.test.js`.
