# v2.9 Linux AI Add-ons Design

**Status:** Approved design; implementation is governed by [the v2.9 Linux AI add-ons plan](../plans/2026-09-01-v2.9-linux-ai-addons.md)

## Goal

Extend v2.9.0 to provide CUDA-backed local transcription, diarization, and user-triggered summaries on one explicitly supported Linux profile: CachyOS x86_64 on Hyprland/Wayland + PipeWire, with an NVIDIA RTX 4070. All other Linux distributions and GPU configurations remain experimental. No cloud processing, telemetry, or CPU fallback is introduced.

## Scope and delivery

Implement this as `feature/v2.9-linux-ai-addons`, created from the accepted v2.9 integration base after the Electron 44 lane and reliability follow-through. The work is a sequential, gated lane rather than one bulk runtime change:

1. Establish CUDA-backed faster-whisper on the supported CachyOS/RTX 4070 profile.
2. Investigate and explicitly accept or reject each Linux diarization engine: Speakrs and token-based Pyannote.
3. Investigate and add a Linux summary runtime only when its packaged setup and hardware gates pass.
4. Run the integrated packaging, repair/removal, cancellation, quit, and sustained-GPU matrix.

The first task in every phase is to re-check official upstream releases, artifacts, licenses, Python/Node compatibility, CUDA major requirements, and hashes. The plan must not preselect a new runtime asset, Pyannote policy, or summary accelerator before that evidence exists.

## Architecture

Linux must reuse the existing main-process services and controls:

- `gpu-runtime-service` owns CUDA runtime detection, installation, repair, removal, and cache invalidation.
- `gpuResourceActionQueue` keeps CUDA-runtime actions, Whisper preload, and GPU compute mutually exclusive.
- `aiComputeActionQueue` remains the single queue for transcription, diarization, and summary generation.
- `ai-addon-state` remains the sole catalog for model/runtime metadata; renderer input never selects artifact URLs, model references, or devices.
- `ai-addon-ipc`, diarization setup, summary setup, and their existing cancellation/finalization paths remain the owner of their IPC contracts.

There will be no Linux-only compute queue, alternate recorder path, cloud operation, or unpinned runtime discovery. The primary recording path stays untouched except for consuming an accepted CUDA transcription result through the existing durable meeting/transcription flow.

## CUDA transcription

The Linux runtime profile must identify a compatible NVIDIA driver and the expected CUDA major at action start, not from a stale UI cache. It must install only catalog-pinned, hash-verified dependencies below `userData`, use a controlled child environment/library path, and report the actual selected device and compute type in meeting metadata. If preflight, runtime integrity, or the smoke test fails, the feature remains unavailable; it must not silently select CPU.

### Hardened Task 2 runtime (adversarial-review remediation)

Linux CUDA remains **disabled by default**. Task 1 is host/candidate investigation only; packaged RTX 4070 evidence is Task 3 and is not started here.

- **Catalog ownership.** The Linux-x64 CUDA 12 closure is code-owned (`src/main-process/linux-cuda-runtime-catalog.js`). Exact wheel versions, filenames, sizes, direct official URLs, SHA-256 values, required extracted libraries, and `x64` architecture are pinned there. A user-writable `install.json` or leftover wheel never authorizes a binary.
- **Install.** Download only the pinned wheels over HTTPS, verify hash and size, then install offline with `pip install --no-index --find-links --target` into `{userData}/ai-addons/cuda/python`. Setup validation and every admitted compute probe full-hash the required managed `.so` files.
- **Loader containment.** Runtime root, library directories, and individual libraries are validated with `lstat`/`realpath`. Symlinks and path escapes are rejected. Inherited `LD_LIBRARY_PATH` is cleared. Driver directories, if retained, come from a narrow canonical allowlist. Empty, relative, duplicate, world-writable, outside-root, and unsafe entries are rejected.
- **Probe.** Unsupported CUDA major is detected only inside the verified managed closure, not from ambient `PATH`. The NVIDIA-device probe is `nvidia-smi --query-gpu=name,driver_version,compute_cap --format=csv,noheader` with structured driver/device/compute-capability output. Missing executable, timeout, nonzero exit, malformed output, invalid child JSON, and a probe child's nonzero exit are `probeError`. The main process preserves the backend `statusCode`. CTranslate2 CUDA initialization runs only after verified library checks.
- **Admission.** Admitted Linux CUDA result JSON must report `device=cuda` and `float16` or `int8_float16`; otherwise `LINUX_CUDA_DEVICE_MISMATCH`. `process.arch === 'x64'` is required. Missing admission resolver keeps Core Beta CPU. Non-ready statuses stay fail-closed with no CPU fallback.
- **Uninstall.** While holding `gpuResourceActionQueue`, atomically rename the active runtime to a tombstone, invalidate the CUDA cache, then delete only the tombstone. Timeout or quit must not continue deletion against the live path.
- **Windows/macOS.** Existing pip/DLL, queue, cancellation, timeout, quit, IPC, and facade export contracts stay unchanged.

## Diarization decision gate

Speakrs and Pyannote remain exclusive engines. Their Linux support is independent:

- Speakrs requires a packaged x86_64 Linux CLI, an integrity check equivalent to existing Windows/macOS checks, a pinned GPU runtime/model-pack setup path, and a guided-transcription smoke.
- Pyannote requires an independently pinned Linux dependency/model path, CUDA runtime validation, and proof that Electron `safeStorage` is encrypted and usable in the supported CachyOS Hyprland session. A token is passed by stdin only, redacted from all diagnostics, and never written to model manifests or meeting metadata.

An engine can be accepted only after its individual gate. A rejected or unvalidated engine stays visible but unavailable with a concise reason; it must not be emulated through another engine or CPU execution.

## Summaries

Summary generation remains user-triggered. The implementation must choose its Linux runtime only after fresh upstream investigation establishes a compatible, redistributable, checksum-pinned artifact. Setup and validation retain HTTPS host allowlists, archive traversal protections, `userData` model caches, full-hash setup validation, sidecar atomicity, source-transcript hashing, and the metadata-phase quit/cancel exemption. The summary runtime must use an accepted GPU profile or remain unavailable; no CPU fallback is added as a workaround.

## Safety and failure handling

All Linux AI paths are fail-closed for unsupported architecture, absent/unsupported NVIDIA driver, wrong CUDA major, unsafe dynamic-library resolution, absent encrypted secret storage, untrusted artifact, checksum mismatch, missing packaged CLI, or failed validation smoke. Existing paths that clear Hugging Face environment variables and redact progress remain mandatory.

Downloads remain catalog-pinned, HTTPS-only, allowlisted, checksum-verified, and extracted with the repository's traversal guards. User-writable manifests cannot authorize binaries, model packs, DLLs, or shared libraries without the catalog-backed integrity checks.

## Validation and release claims

Automated tests must cover catalog selection, platform policy, child environments, queue admission, cancellation, repair/removal, integrity rejection, and token isolation without weakening Windows/macOS tests. CI without a GPU is coverage-only and must not claim hardware acceptance.

The supported CachyOS/RTX 4070 matrix requires packaged evidence for:

- CUDA Whisper preload and transcription, including persisted device/compute metadata;
- each accepted diarization engine's setup, guided transcription, cancellation, removal/repair, and token safety;
- summary setup, generation, cancellation, quit during metadata finalization, and stale-summary handling;
- concurrent-work exclusion, interruption recovery, and a bounded GPU/VRAM soak;
- app packaging and its existing Linux AppImage, pacman, and deb verifier.

Only after the matching evidence passes may the UI present the component as available on the supported profile. CachyOS without the validated NVIDIA profile, Omarchy, and all other Linux distributions remain experimental/unavailable for Linux AI until independently validated.

## Release sequencing

The Electron 44 lane stays an isolated compatibility lane. Before its merge, correct the Markdown whitespace failure, run the full local gate, push the exact commit, and require CI. After the Electron merge, the order is reliability follow-through, this Linux-AI lane, capture modes, then `release/v2.9.0` integration. Release metadata changes only on the release branch after all accepted lanes are independently green.
