### Cross-platform recorder findings from the Linux Phase 3 review (2026-08-25)

Surfaced while reviewing `linux_recorder.py` but **out of scope for the Linux Core Beta** — each one lives in shared or Windows/macOS code, so fixing it means re-validating those platforms on hardware we did not have during the Linux work. None of these block Phases 3–5. Revisit as a separate cross-platform recorder pass.

- [ ] [Risk: Medium] **macOS discards committed desktop audio on a late capture failure.** `macos_recorder.py:_close_capture_spools_for_mix` sets `includeDesktop = false` whenever `_desktop_runtime_failure` is set, so a Swift helper crash at minute 59 of a 60-minute meeting throws away all 59 minutes of already-committed desktop audio rather than mixing the truncated track. Linux was changed to keep those frames (only a *spool* failure now excludes the track); macOS was deliberately left alone because a crashed helper's partial data is more suspect than a vanished Pulse monitor's. Decide whether macOS should adopt the same keep-what-was-committed rule. The mixer already zero-fills past the end of a short desktop track, so the finalizer needs no change. Needs Mac hardware to validate.
- [ ] [Risk: Low] **macOS and Linux final files run slightly longer than the microphone timeline.** When desktop capture starts after the mic, `_close_capture_spools_for_mix` pads the desktop spool to `mic_frames` *and* the manifest records `desktopLeadingPadFrames`, so the max-padding profiles total `mic_frames + desk_pad` — the saved meeting ends with roughly the desktop start offset (tens of milliseconds) of trailing silence. `windows-v1` is unaffected because `_aligned_frame_count` hard-caps it at the mic timeline. Correct fix is to pad the desktop spool to `mic_frames - desk_pad`, but it touches the shared `macos-v1`/`linux-v1` mix geometry and its duration-expectation tests (`expected_output_duration_seconds`, capture-recovery truncation checks), so it wants its own change with macOS re-validated on hardware.
- [ ] [Risk: Low] **`output_path.replace('.wav', '.opus')` replaces every occurrence, not the extension.** In `_resolve_recoverable_output_path` on macOS (`macos_recorder.py:1030`) and Linux (`linux_recorder.py:954`); Windows has no equivalent helper and resolves recovery through the module-level `_final_output_path` instead. A recordings directory whose own name contains `.wav` would produce a corrupted recovery path and a failed or misdirected recovery. Not reachable with the current `userData/recordings` layout, so it is latent rather than live. Fix with a suffix-anchored replacement (or `Path.with_suffix`) in both, plus a test using a `.wav`-containing parent directory.
- [ ] [Risk: Medium] **Mic-thread failure at stop skips finalization even though the mic spool is complete and on disk.** All three recorders close and commit the spools and *then* check for a capture-thread error — macOS and Linux via `_resolve_async_recording_failure()` returning a `success:false` payload with no output path, Windows via `get_async_capture_error()` raising out of `stop_recording` — leaving a fully committed microphone track that only next-launch capture recovery will turn into a meeting. The user sees a failed recording and has to accept a recovery prompt on the next start. This is current cross-platform contract (Linux was written to match), not a Linux regression, so it was left as-is. Consider finalizing the committed mic track and reporting the mic failure as a warning instead, keeping the hard failure only when nothing was committed.
